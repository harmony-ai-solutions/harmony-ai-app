# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

### Under the Hood

#### Added
- **Voice cloning, voice design, TextGen WebUI preset saving, and realtime AutoVAD pipeline (config-and-partner-ux-rework).** The **Text-to-Speech** config screen now supports zero-shot **Voice Cloning** with reference-audio recording, speaker-embedding generation, and a 2D speaker-embedding heatmap on **Soulbits Cloud** and **Soulvoice**, **Named Voice Profiles** (`/api/voices` load/save/delete), model-gated acoustic and prosody tuning (Pitch, Speed, Energy, Style, Seed for OpenVoice/HarmonySpeech; Exaggeration, CFG Weight, Loudness Normalization, and paralinguistic tag chips for Chatterbox), **ElevenLabs Instant Voice Cloning & Voice Design** (prompt-to-voice previews + save) alongside Scribe STT, **OpenAI Voice Design Instructions** (`gpt-4o-mini-tts`), and a stateless **Direct Voice Test Studio** so you can preview speech directly inside the config editor. On LLM modules (**Backend**, **Cognition**, **Movement**, **Vision**), the **Sampling Preset** bar now includes a **Save as… / Import YAML** modal to save your tuned hyperparameters as a named TextGen WebUI YAML preset or delete custom presets. On **Speech-to-Text**, a two-stage **Realtime Audio Pipeline (`Stage 1: VAD Voice Gate ➔ Stage 2: Transcription on Speech`)** switcher replaces the multi-card wall and surfaces live `STT_SPEECH_STARTED` / `STT_SPEECH_STOPPED` voice-detection indicators and realtime VAD segment bars in the test studio.
- **Shared provider accounts + in-app key testing (provider-registry 6-1…6-3).** API credentials are now **shared provider accounts**: enter a key (and endpoint) **once** on a new Settings → **Providers** screen and every module config can reuse it — no more re-typing a key per module. Accounts are grouped by provider type with the key masked, an **in-use badge**, and a **Test key** action that runs the engine's credential probe and shows a six-state verdict (**valid / invalid / throttled / blocked / scope-limited / unreachable**) plus provider extras (ElevenLabs tier + character quota, OpenRouter budgets, ComfyUI VRAM, versions); the test auto-runs after save. Deleting an account a live module config still references is blocked, listing the referencing configs. The module-config editor is now **Provider → Account → Capability → Module**, with an account picker that collapses when there is only one account, **catalog-backed model pickers** plus an on-demand **Fetch from provider** live refresh (provenance chips + a retained **Custom…** escape), an ElevenLabs voice picker, and STT **transcription / VAD** slots that no longer share one provider list (VAD offers only Soulbits Cloud + Soulvoice). All over the engine's accounts API (management contract **1.6.0**).
- **Live model lists, sampling presets, and Mistral / Ollama / LocalAI (provider-registry 2-1/2-2/6-5).** Free-text model fields became **pickers** fed by the engine's capability catalog (offline-first) with a live fetch on demand; the blind `sampling_preset_name` text box became a **preset dropdown** fed by the engine's presets — a preset supplies **defaults** and your explicit values win (the UI previews what a preset sets). **Mistral, Ollama (incl. experimental STT) and LocalAI** are selectable across the modules they serve, and Google/xAI gained their new params (thinking, image model).
- **Seeded Soulbits Cloud defaults (provider-registry 6-4).** A fresh sign-in is seeded with ready-to-use Soulbits Cloud configs for every module (both STT slots included), and the app keeps the cloud account's credential current on **every** sign-in and token renewal — plus gap-fills any default config you deleted, without ever overwriting the ones you keep.
- **QR-first desktop pairing + delegated enrollment intake (plan 7-15).** Scanning a desktop QR is now the primary pairing gesture, and a signed-out full-variant phone can adopt the desktop's account over the same LAN pairing — no typing, no shared secret. The pairing-payload parser became a **discriminated union** (`parseSyncPairingPayloadV2` in `src/services/sync/syncCloudTypes.ts`): the unchanged cloud shape (`{relay_url, pairing_token, account_hint}` — portal + desktop `POST /api/sync/pairing/cloud` are identical) parses as the cloud kind (the legacy `parseSyncPairingPayload` delegates to it and stays cloud-only), and the new `{v:1, kind:"soulbits-lan", ws, wss?, mode, fingerprint?, dataset_id, name, secret, ttl, enrollment?}` object parses as the LAN kind (tolerant of a missing `wss`/`fingerprint`/`enrollment`; a malformed enrollment block is dropped rather than failing the payload). `DesktopSyncScreen`'s shared `handleScanned` routes by kind — cloud → the existing account-verified relay pairing; `soulbits-lan` → a new **confirmation sheet** (`LanPairingConfirmSheet`) showing the desktop name, the transport mode in plain language with a short (8-hex) certificate fingerprint, and the dataset; confirming applies **ONE** `PUT /api/sync/client` patch (`{transport:'lan', peer_address:ws, peer_wss_address:wss?, security_mode:mode, peer_fingerprint:fingerprint?, lan_pairing_secret:secret, device_name, enabled:true}`) so the engine dials and the desktop auto-approves via the single-use secret. The pairing card is now the **prominent top card** with a big **Scan desktop QR** CTA accepting both kinds; the manual LAN form (peer addresses + the three equal security modes) collapses under an **Advanced** disclosure (semantics unchanged — unencrypted stays first-class); the cloud manual-paste surface is unchanged. **Delegated enrollment (full variant):** when the LAN payload carries an `enrollment` block, a signed-out phone also exchanges the grant at `POST /v1/auth/device/enroll` (cloud base from `src/config/cloud.ts`, device id from `DeviceIdProvider`, platform `android`/`ios`) and persists the returned session through the **same** `AuthService` token path every login uses (`enrollDevice` → `handleTokenResponse`; no parallel token path); a signed-in **matching** account (masked hint, `maskedAccountHintMatches`) just pairs; a signed-in **different** account is warned and enrollment is skipped; and an exchange failure never blocks pairing (surfaced as a toast). **Store variant:** LAN payloads are rejected with clear copy ("This connection type isn't available in this version") as defense in depth (no LAN anywhere in store). Management contract bumped **1.4.0 → 1.5.0** in lockstep (engine openapi + canonical fixtures + vendored typed fixtures + drift CLI: 39 endpoints / 43 fixtures); `EngineApiClient` gains `peer_fingerprint`/`lan_pairing_secret` on the config patch + `peer_fingerprint` on the status config, plus `mintLanPairing`/`mintCloudPairing`/`cloudAccount`/`startCloudSignIn`/`verifyCloudDevice`/`cloudSignOut`. Secrets/grants are never persisted or logged beyond the single engine-owned config write. See `docs/CONNECTION-SECURITY.md` for the fingerprint-pinning, single-use-secret and unencrypted-caveat semantics. New i18n keys under `desktopSync` (en; other locales fall back to en).
- **Build-time engine-contract gate.** `npm run android` / `android-prod` / `ios` / `build:e2e:android` now fail fast when the app's pinned management-contract version does not match the embedded engine checkout's `docs/api/management/openapi.yaml` (`scripts/check-engine-contract-build.cjs`, also runnable standalone as `npm run check:engine-contract`). The engine ships WITH the app, so a contract mismatch is a build defect, not something a running app can fix; when the engine checkout is absent the check is skipped with a warning (app-only CI).
- **Local Android dev auto-provisions Soulbits Engine.** `npm run android` runs a `preandroid` step (`scripts/build-engine-sidecar.cjs`) that builds Android `libengine.so` from a sibling `harmony-link-private` checkout only when missing/stale, then vendors it into `jniLibs/`; the run then builds, installs and starts Metro — no manual `-PENGINE_SIDECAR_*` flags locally (CI/release unchanged). Overrides: `SOULBITS_ENGINE_REPO`, `ENGINE_SIDECAR_REBUILD=1`.
- **Faster CI release builds (Gradle dependency + build cache, engine-sidecar cache, leaner release steps).** The Android release legs were fully cold every run — every `~/.gradle` dependency and every compiled task output was recomputed from zero, and the engine sidecar (~115 MB across both ABIs) was re-downloaded per leg. The workflow now runs `gradle/actions/setup-gradle` (restores dependencies, transforms and the local build cache onto each fresh runner; writes enabled because dispatch runs land on a feature branch where the action would otherwise be restore-only) alongside `org.gradle.caching=true` (task outputs become cross-run FROM-CACHE hits), caches `android/app/src/main/jniLibs` keyed on the pinned engine version (the `vendorEngineSidecar` task already skips when the `.so` files exist), passes the release version as `-PVERSION_NAME` instead of `sed`-rewriting `app/build.gradle` (which also permanently defeated any future configuration-cache reuse), gives Metro an explicit 2 workers on the 2-vCPU runners (`-PMETRO_MAX_WORKERS=2`, opt-in so local builds keep full parallelism), uses `npm ci --prefer-offline --no-audit --no-fund`, and updates the S3 `latest` APK pointer with a server-side copy of the already-uploaded versioned object instead of re-uploading the ~75 MB APK. No app behavior change; expect warm release legs ~2.5–5 min faster (measure via the setup-gradle job summary — first post-change run only warms the cache).
- **Release dispatch can now pick which environments to build (`build_environments`).** A manual `Build Release` dispatch takes a new `build_environments` input — `dev` (default), `prod`, or `both` — that drives the Android build matrix (and the iOS matrix, when `build_ios` is enabled, so `dev` + `build_ios` no longer pays for a prod IPA nobody asked for). Release tags are unaffected and always build both environments, so `create-release`'s download table never links a missing artifact. Because a dispatch no longer always builds both APKs, a dev-only run halves dispatch CI cost and wall-clock time (each Android leg is a cold-ish ~2.5–5 min; iOS legs bill at 10× the Linux rate). The `publish-manifest` job now mirrors the selector: it writes `app/dev/latest.json` only when dev was actually built (a prod-only dispatch logs `::notice::dev not built in this run — skipping the dev channel manifest` instead of linking a non-existent APK). The **prod channel manifest stays tag-only** by design — a prod-only dispatch uploads the versioned prod APK but publishes no prod manifest and logs an explicit notice, so prod-channel installs are never advertised to from a dispatch. No app behavior change.
- **Two distribution variants — Store vs Full (plan 7-14).** The app can now be built as either a **store** listing (Play / App Store) or the **full** self-built / sideload release, selected by a single build-time axis `APP_VARIANT` (`store` | `full`; default `full`), which also derives `APP_CHANNEL` (`store` → `play`, `full` → `sideload`) and stays orthogonal to `APP_ENV`. A **store** build is a Soulbits-Cloud-only product: a forced sign-in wall at launch (a one-tap silent Google/SIWA attempt first, then a full-screen, non-dismissible wall; signing out returns to the wall), provider pickers collapsed to **Soulbits Cloud** (other providers unavailable; non-cloud entity configs are visible-but-**locked** with neutral copy — the runtime lock never writes the synced `is_disabled` flag, so it can't disable entities on desktop/sideload devices), cloud-relay pairing only (the direct-LAN QR path is hidden), **purchases disabled at launch** (the wallet balance stays visible and the Market stays browsable, but "Buy/Sell Souls", the marketplace buy/checkout button, and the Billing & Purchases settings entry are hidden; Apple/Google in-app purchase is a separate future plan), and the **in-app APK self-updater OFF** — the store listing owns updates, so there are no update checks, and the blocking "engine too old" card is removed entirely (the engine ships with the app, so there is nothing to update at runtime). A **full** build is byte-for-byte today's behavior: every provider, direct-LAN pairing, purchases, and the sideload APK self-updater. **Zero steering** holds throughout store builds (no "download the app/APK" or portal-install CTAs anywhere). Both variants share the **same application ids** (`ai.soulbits.chat` / `ai.soulbits.chat.dev`) — the variant is a build-time flag, not a package suffix, so store and full builds are **not co-installable** side by side; a self-built build with nothing configured stays **full**. Android gains `devStore` / `prodStore` flavours (`assembleDevStoreDebug` / `assembleProdStoreRelease`; the existing `dev`/`prod` tasks are unchanged); iOS selects the variant via `npm run oauth:dev -- --variant=store` (written into the generated `.env`). Engine + cloud are untouched (variant-agnostic) and the management contract stays **1.4.0**.
- **Outreach notification delivery — engine events stream, local + relay surfaces, Firebase (plan 7-12).** When an AI companion messages the user while no frontend is focused, the app can now notify the device they're actually holding — including outreach that arrives by **sync** from a desktop authority, which previously applied silently. The engine gained a management-WebSocket outreach stream (`GET /api/notifications/stream`; `{type, entity_id, entity_name, message_id, title, body_preview, created_at, eligibility, delivery?}`, `delivery:"live"` on eventserver live-path events; loopback-token + admin-key auth per the 7-11 log-WS pattern, engine never relays it to the cloud). The app subscribes with a new `OutreachNotificationService` (injectable WS factory, capped-backoff reconnect, dies gracefully engine-less) and routes per `AppState`: **foreground** → in-app surfacing only (no banner spam); **background/process alive** → a **local OS notification** through new native surfaces — iOS `SoulbitsNotifications` gains local posting and a new hand-rolled Android `NotificationsModule` (per-entity channels, `requestAuthorization`/`getAuthorizationStatus` parity incl. the Android 13+ `POST_NOTIFICATIONS` runtime grant) — **no new JS dependency**. Engine gates stay authoritative (mute/decay decided engine-side; `eligibility` is a defensive second check) and every notification — engine push, relay push, local post — collapses per `message_id` through a shared short-window `outreachDedupe` seam. New Settings → **Notifications** delivery surface (`NotificationSettingsScreen`): `notification_transport: auto | direct | cloud | off` (default `auto`; "cloud is a convenience, never required" framing) plus a **Hide content on lock screen** toggle (default off = preview shown, generic text when on); new `settings` i18n keys (en). **iOS wake relay:** the wake pass now also covers sync-applied outreach — a short-lived `SyncAppliedOutreachCollector` subscribes while catch-up/batch applies, and relayed events are gated by transport (`auto`/`cloud` relay; `direct`/`off` skip) and by a persisted `OutreachRelayWatermark` (engine `created_at` high-water mark, mirroring the engine observer so re-applies never re-notify); the device-authored relay payload gains `messageId` (`{kind:"outreach", entityId, messageId}` — additive; cloud stays blind). **Direct/custom-FCM (topology A):** the RN `INIT_ENTITY` session params now carry `push_token` (engine-targeted/direct sessions only — cloud conduct-proxy sessions are fenced off this store) from a single `PushTokenStore` (SDK FCM token wins over the native raw-APNs fallback). **Firebase (D1=b/D2/D4):** `@react-native-firebase/app` + `messaging@26.4.0` (modular API) acquire an FCM registration token on both platforms → registered with the cloud (`DeviceAuthService.registerDevice`) and forwarded to a directly paired engine; placeholder `google-services.json`/`GoogleService-Info.plist` ship by default and the whole path is runtime-guarded (`getApps()`/`getToken()` failures keep the native fallback — a SDK-less build degrades gracefully); foreground arrivals are suppressed + deduped and silent keepalives route into the existing native wake bridge unchanged. **Engine-contract 1.3.0 → 1.4.0** in lockstep (engine openapi + canonical fixtures + app vendored fixtures + `ENGINE_CONTRACT_VERSION`; drift CLI green). New unit suites cover the service, settings, dedupe, watermark, collector, token store, Firebase messaging and the wake-relay extension. **Owner gates:** real Firebase project config + APNs auth-key upload, `pod install` on macOS (RNFB), the staging push round-trip, and device drills (Android background local + mute; desktop D3; iOS killed-app next-wake relay; topology A direct drill + dedupe; lock-screen toggle).
- **Engine log viewer + diagnostics export (plan 7-11).** The app can now see the embedded engine's logs — the capability the desktop Dev-Tools Log Viewer had and the app lacked (and, before the engine half, embedded compositions captured *no* logs at all). Settings → Help & Support gains an **Engine logs** row opening `EngineLogScreen`: a live tail over the engine's WS log stream with follow/pause, a REST ring-buffer backfill on load + "load older" pagination, level/component/entity/search/prompt-only + prompt-type filters, dedup-count badges driven by stream remove events, a ~250 ms render-batch coalescer, and a 2 000-row in-memory cap. A collapsed **Verbosity** section reads/writes the engine's runtime log-level config (`GET/PUT /api/development/logs/level`) with a battery/log-volume warning. A **Share diagnostics** action builds a report — app version, running engine version (via 7-10's `engineAppVersion()`), management-contract version, platform/OS, device model + a log dump (current filter window) — writes it to the cache dir with `react-native-fs`, and opens the OS share sheet via the new `react-native-share` dependency; long-press a row to copy it. `EngineApiClient` gains `engineLogs`/`engineLogCount`/`engineLogComponents`/`engineLogEntities`/`engineLogPromptTypes`/`engineLogLevels`/`setEngineLogLevels` + the `EngineLogEntryDto`/`EngineLogQuery`/`EngineLogLevelConfigDto` DTOs (the log entry is camelCase — the engine's `logging.LogEntry` JSON); a new `EngineLogStream` WS client (`ws://…:<adminPort>/api/development/logs/stream?token=<loopback>`, capped-backoff reconnect). The 7 endpoints join `REQUIRED_ENGINE_ENDPOINTS` + the vendored fixtures (engine canonical fixtures updated in lockstep; **no contract-version bump** — the routes are long-existing, only their auth scope moved to the loopback token). New i18n namespace `engineLogs` (en). Privacy: nothing is uploaded; the dump is the user's own data shared through the explicit OS sheet. Unit tests: client methods, stream client, screen filter logic, report builder, manifest conformance. **Owner gates:** `react-native-share` native sign-off (pods + gradle) and on-device drills.
- **Engine & app update surfacing + release provisioning (plan 7-10).** The release pipelines now actually ship an engine and the app knows what it is running. Engine CI publishes the sidecar (`engine/<v>/<abi>/libengine.so`, both ABIs), the gomobile facades (`SoulbitsEngine.xcframework.zip` / `SoulbitsEngine.aar`) and both release manifests (`engine/<v>/manifest.json` + `engine/latest.json`) to the existing `soulbits-releases` bucket, then verifies the set with `aws s3 ls`; the app release workflow takes an `engine_version` input, passes `-PENGINE_SIDECAR_VERSION`/`-PENGINE_SIDECAR_BASE_URL` + `-PENGINE_SIDECAR_STRICT=true` to gradle (a missing sidecar now **fails** the build instead of shipping engine-less), asserts `libengine.so` inside the APK, fetches the iOS xcframework before `pod install`, and writes `app/latest.json` from the tag-only `create-release` job. The fictional gradle `ENGINE_SIDECAR_VERSION` default (`0.1.0`) is retired (CI-required explicitness). At runtime, `EngineApiClient.engineAppVersion()` + a new `semver` util (`v0.3.0-dev` < `0.3.0`) drive an `EngineService` contract canary (`ok`/`too_old`/`unknown`) that renders a **blocking** "update the app" card (reusing the DesktopSync rejected-card language) when the running engine is too old; a new `UpdateAvailableService` fetches both manifests (6h AsyncStorage cache, cache-busted `?t=`, env/flavor-aware) and powers dismissible per-version banners; the Settings About block gains App / Soulbits Engine / management-contract version rows; and the DesktopSync rejected state gains a "download the latest desktop engine" deep-link from `engine/latest.json`. An optional Android in-app APK self-update lands behind a channel flag (`sideload` only; Play-channel builds hide it; iOS links to the portal INSTALLATION instructions). No management-contract changes. New i18n namespace `updates` (en). Manifest URLs are a de-facto public contract (owner sign-off).
- **Engine management-API data layer (internal, flag-gated).** The app can now read its local data from the embedded engine's management API instead of the on-device SQLite replica. A new `EngineApiClient` plus a repository seam (`src/database/repositories/index.ts`) select the implementation per call via the `ENGINE_API_DATA_LAYER` flag (default off). On the consolidated 3-1b surface (`/api/entities/:id/{chat-list,conversations/:participantKey/messages,interactions,emoji-actions,emotion,memories}`, `/api/messages/:id` + byte endpoints, `/api/character-profiles/*`, `/api/providers`, `/api/module-configs/*`) the layer now covers: chat list + message windows, interactions, emoji actions, emotion and memory reads; character/entity/module/provider read surfaces; character favorites; and the message/emoji/chat-settings writes. Functions the engine authors (message create, interactions/emotion/memory writes) and id-only signatures with no engine route stay on the SQLite path (see the 3-2 report). No user-visible change while the flag is off.
- **Cloud-mode on-device engine orchestration (internal, flag-gated).** When signed in with a SoulbitsCloud account, startup can now run the embedded engine on-device and refresh the SoulbitsCloud provider configs locally, instead of provisioning a cloud engine session. The new `cloudModeOrchestration` module (flag `ENGINE_CLOUD_MODE_ON_DEVICE`, default off) starts the engine, injects the fresh cloud token as a direct local write, and fetches the tier's `autonomy_beats_per_day` budget for on-device lifecycle. No user-visible change while the flag is off; the legacy cloud-session path (`CloudSessionService`) stays authoritative until 3-4 removes it. Engine feature flags are now hydrated from storage at boot. (The provider-config injection depends on an engine-side management route still to land — see the 2-5 report.)
- **Provider-config writes + character stats now flow through the engine's management API (internal, flag-gated).** The `ENGINE_API_DATA_LAYER` adapters gained the full provider-config write surface (create/update/delete across all 16 provider types over `POST/PUT/DELETE /api/providers`, with the engine's `provider_in_use` 409 surfaced as the app's in-use error) and `getCharacterStats` over the new cross-entity `GET /api/stats/characters`. Unit-tested against the mock management server. No user-visible change while the flag is off.
- **The app's data layer is now the embedded engine's management API (task 3-4 relink; `ENGINE_API_DATA_LAYER` default ON).** Every repository call — reads AND writes — now resolves to the management-API adapters (`src/services/engine/repositories/*`); the repository seam (`src/database/repositories/index.ts`) is a pure re-export with no SQLite fallback. The remaining create/authoring writes were relinked to the engine's **create-then-use-response** contract (the engine mints entity + character-profile ids): `CreateAIScreen`, `CharacterChatService`, `CharacterCardImportService`, `createUserPersona`/`createUserPersonaFromCard`, and `duplicateAIPartner`. Module configs are mapped between the engine's composite shape and the app's flat `provider_config_id` model, and character images upload as **multipart** (`FormData`). The app now **requires the embedded engine** (sidecar/iOS facade mandatory — engine-required sequencing for 4-2/4-3). The legacy TS SQLite stack, sync/cloud-session services and rows-v1 protocol are now dead code pending the 3-4 deletion PR (see `.current_work/app-engine-parity/3-4-deletion-manifest.md`); D-35 send/ingest and the deletion blast radius remain outstanding.
- **The TS SQLite/sync/cloud stack is DELETED (task 3-4).** The on-device SQLite replica, its 47 mirrored migrations, the SQLite repository layer, `SyncService` + the rows-v1 protocol, `CloudSessionService` + the cloud-session/broker path, the wipe/rebuild machinery (`WipeRebuildFlag`, `react-native-restart`), the estimate-confirm helpers, and the schema-parity tooling are all gone — the embedded engine's management API is the single data layer. `SyncConnectionContext` is now an engine-connection status context; the sync/cloud settings + connection-setup screens and the cloud provisioning/purge components are removed. **D-35 message authorship** now renders outgoing messages as optimistic in-memory pending rows (no SQLite mirror, no app-authored engine ids) reconciled against engine reads, with incoming messages driven by engine events. **Mute is engine-authoritative** (`PUT /api/entities/:id` `is_muted`; the app-local AsyncStorage overlay is deleted). Dependencies dropped: `react-native-sqlite-storage`, `react-native-restart`, `better-sqlite3` (+ their `@types`). 43 test suites were removed with the stack; the jest config is a single `unit` project. Engine-required sequencing for 4-2/4-3: iOS builds need the in-process facade in the same release, or the release is Android-first (5-3).
- **`DesktopSyncScreen` visual language reconciled with the deleted rows-v1 sync screens (task 3-5b).** The changeset-v1 desktop-sync settings screen now reuses the design/component language of the deleted `SyncSettingsScreen`/`ConnectionSetupScreen` — the hero connection-status orb (glow rings + gradient orb + state icon/label/subtext), icon-labelled detail rows with dividers, and the security shield badge — while keeping the new semantics (9-state badge, pending-writes warning, authority indicator, pairing hint, connect/disconnect/disable/hand-over actions). Old-protocol logic (sync estimates, table selection, wipe/rebuild, broker/provisioning states) stays dead. Screen test updated for the new hero; all existing testIDs preserved.
- **User-owned-storage backup & restore (plan 2-6).** A new `src/services/backup/` layer coordinates encrypted engine snapshots to the user's **own** cloud storage — the operator stores no user database data. `BackupOrchestrator` owns settings (AsyncStorage), credentials (react-native-keychain), the W1 account-escrow call, target-descriptor construction, the manual/automatic run, restore unlock-material resolution, and native scheduling; `BackupKeyEscrow` wraps the 2-5 `PUT/GET/DELETE /v1/account/backup-key` endpoints. A new **Backup & Restore** settings screen (`BackupSettingsScreen`) exposes the target picker, cadence, Wi-Fi-only/charging, size display, "back up now" (with an exact-size estimate-confirm dialog), recovery-code display/reset, passphrase opt-in (W4), and per-target status; a fresh-install **restore onboarding** screen (`RestoreOnboardingScreen`) drives the restore flow. Android gains a `HarmonyBackup` native module (SAF folder picker, WorkManager daily job with constraints + a headless `HarmonyBackupTask`, share-sheet export, Dropbox/OneDrive OAuth 2 + PKCE), and the manifest gains `dataExtractionRules` that exclude the engine dir (DB + staging + RAG) from Auto Backup while including it in device-to-device transfer. `EngineApiClient` gains the `/api/backup/*` methods. Honest-limits copy follows research §3.5. iOS iCloud-container + W2 keychain land with 4-2 (below); Google Drive remains a consent-gated stub.
- **Fresh-install restore offer is now wired (5-3).** After a fresh install's first sign-in the app probes for a restorable backup — the iOS iCloud container metadata, or (on Android/desktop) the target recorded in persisted settings plus the account's escrowed backup key (W1) — and, when one is found, shows a **skippable** restore offer (backup date, size and target) before the normal post-sign-in destination; "Start fresh" leaves the standard path untouched. The W1 account-escrow path is now wired to the live cloud token (the orchestrator's token provider was previously unset, so "sign in and restore" silently fell back to the recovery code); a new `hasEscrowedKey()` probe backs the gate.
- **Soulbits Cloud hosted backup target + quota display (plan 7-5).** The backup **target picker** now offers **Soulbits Cloud** — zero-setup hosted storage for signed-in cloud-account users, shown only when signed in. `BackupOrchestrator.buildTargetDescriptor` injects the account PASETO (the 7-3 `relay_token` pattern; the engine never authenticates to Soulbits itself), the sync-relay backup base (`SYNC_RELAY.backupBaseUrl`), and a stable per-account backup slot into the engine's `soulbits-cloud` target descriptor; on a hosted `401` it refreshes the PASETO and retries once (mirroring 7-3's auth-needed recovery). The settings screen shows the tier's hosted usage (`getCloudQuota()` reads `backup_bytes` + `quotas.backup_storage_mb` from the relay's `/v1/sync/status`) as "Y / Z used", and the hosted target is a first-class restore source alongside iCloud/WebDAV/etc. Engine-contract version **unchanged (1.1.0)** — the backup routes are not part of the pinned contract and no sync endpoint/schema grew. New i18n keys under the `backup` namespace; unit tests cover the descriptor, the quota read, and the 401 refresh-and-retry.

- **Cloud-sync status now shows the tier limits proactively (plan 7-6).** The cloud-sync status card surfaces the account tier's **device cap** and **buffer usage** before the user hits a wall, instead of only reacting to `quota_exceeded`.
