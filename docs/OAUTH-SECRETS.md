# Google OAuth Client Secrets — Environment Wiring

This document explains how the app wires Google OAuth client secrets for
**separate Dev and Prod environments** without ever committing credentials.

## Quick Start (Local Dev)

```bash
# 1. Drop the GCP OAuth client JSON somewhere matching client_secret_*.json
#    (repo root or secrets/dev/ — see Search Order below)

# 2. Load it for the dev environment:
npm run oauth:dev

# 3. Build / run as usual:
npm run android     # runs oauth:dev automatically
npm run ios         # runs oauth:dev automatically
```

## Missing Secret File — Builds Still Work

The build scripts (`android`, `android-prod`, `ios`) call the loader with
`--if-missing-ok`: if no `client_secret_*.json` is present the loader prints a
warning and **exits 0**, so the native build proceeds. Google Sign-In simply
degrades to SDK auto-discovery (`GOOGLE_WEB_CLIENT_ID` empty) — the app
builds and runs; only iOS offline access / OAuth-driven idToken minting may be
limited until you add the secret and re-run `npm run oauth:dev`.

Run the loader manually (without `--if-missing-ok`) whenever you DO have a
secret file, to regenerate `.env` + `android/gradle-secrets.<env>.properties`:
```

```bash
npm run oauth:dev      # fails with a clear message if no secret is found
npm run oauth:dev -- --if-missing-ok   # exit 0 + warn when absent
```

The loader writes two **gitignored** derived files:

| File | Purpose |
|------|---------|
| `.env` | Read by react-native-config on iOS + Metro |
| `android/gradle-secrets.dev.properties` | Read by `android/app/build.gradle` productFlavors |

## Security

- **Never commit** `client_secret_*.json` (see [.gitignore](../.gitignore)
  `client_secret_*.json` + `**/client_secret_*.json`).
- The loader's derived outputs (`.env`, `android/gradle-secrets.*.properties`)
  are also gitignored.
- No OAuth client ID is hardcoded in any tracked file.
- The only values that ship in client binaries are the **client IDs**
  (which are public by design — the *client secret* never reaches the app;
  it is used server-side by the backend).

## How It Works

### scripts/oauth-secrets.cjs

The loader:

1. Resolves the GCP client secret JSON for the target environment
   (`dev` or `prod`).
2. Parses the `client_id` from the JSON (`web`, `installed`, `android`, or
   `ios` sections — Google Console downloads any of these shapes).
3. **Resolves the Web/OAuth client ID** — the value passed to the mobile SDK
   (`GoogleSignin.configure({ webClientId })`) must be a **Web** OAuth client
   ID, NOT an `installed`/Desktop one. If the secret JSON has a `web` section
   its `client_id` is used. Otherwise (e.g. the `installed` desktop client
   provided for dev) the loader falls back to the `CLIENT_ID` in the
   environment's iOS `GoogleService-Info` plist — the authoritative
   per-environment Web/OAuth client ID whose reversed ID is already
   registered as the `CFBundleURLScheme`.
4. Writes a derived root `.env` (with `APP_ENV`, `IS_BETA`,
   `GOOGLE_WEB_CLIENT_ID`, `APPLE_SERVICES_ID`).
5. Writes `android/gradle-secrets.<env>.properties` with the same
   `GOOGLE_WEB_CLIENT_ID`/`APPLE_SERVICES_ID` for the Android flavors.

> **Why not the raw `installed` client ID?** Passing a Desktop client ID as
> `webClientId` makes the Google Sign-In SDK return `idToken = null` after the
> user picks an email — the exact "Google Sign-In failed / no idToken" error.
> Only a Web (or correctly-configured native) OAuth client can mint a mobile
> `idToken`.

### Android (`android/app/build.gradle`)

The `productFlavors` block resolves OAuth values in this priority:

1. `-PGOOGLE_WEB_CLIENT_ID` / `-PAPPLE_SERVICES_ID` (CI / CLI override —
   e.g. `.github/workflows/build-release.yml` passes
   `vars.GOOGLE_WEB_CLIENT_ID`).
2. `android/gradle-secrets.<flavor>.properties` (generated by the loader).
3. Empty string (SDK auto-discovery fallback).

Nothing is hardcoded in a tracked file. `android/gradle.properties` no longer
contains a client ID.

### iOS

- The **single Xcode scheme** uses react-native-config, which reads the
  generated root `.env` (repo root). `npm run ios` and `npm run oauth:*`
  regenerate it.
- `GoogleService-Info.plist` (prod) and `GoogleService-Info-Dev.plist` (dev)
  are both present and contain only **public client IDs** + reversed IDs.
  Both reversed client IDs are registered as `CFBundleURLSchemes` in
  `Info.plist`, so dev/prod OAuth redirects both work.
- CI regenerates `.env` per environment with `APP_ENV` (see
  `.github/workflows/build-release.yml`).

### Android — `google-services.json` (REQUIRED)

Android Google Sign-In does **NOT** use `GOOGLE_WEB_CLIENT_ID`. The SDK
auto-discovers its OAuth client from [`android/app/google-services.json`](../android/app/google-services.json)
at build time (processed by the `com.google.gms.google-services` plugin).

**If that file is still the placeholder** (all zeros / `soulbits-placeholder`),
Android sign-in will return `idToken = null` even though the app builds.
The build prints a loud WARNING when the placeholder is detected.

To fix (one-time, owner action):

1. In Google Cloud Console → the `soulbits-cloud` project → **APIs &
   Services → Credentials**, create **Android** OAuth clients for BOTH
   package names:
   - `ai.soulbits.chat` (prod)
   - `ai.soulbits.chat.dev` (dev)
2. Register each package's **debug + release SHA-1** certificate
   fingerprints (dev debug SHA-1: `5E:8F:16:06:2E:A3:CD:2C:4A:0D:54:78:76:BA:A6:F3:8C:AB:F6:25`).
3. Download the project's `google-services.json` (Firebase console → project
   settings → "Google services" → `google-services.json`), which contains
   both Android client entries + the Web client entry (`client_type: 3`)
   that the SDK uses to mint the `idToken`.
4. Replace [`android/app/google-services.json`](../android/app/google-services.json).

> This file is intentionally tracked (it is not a secret) — but it MUST be
> the real one. The placeholder is only there so the Gradle plugin does not
> fail the build before the owner supplies credentials.

### Runtime (`src/config/cloud.ts`)

- `OAUTH.googleWebClientId` / `OAUTH.appleServicesId` come from
  react-native-config (build-injected, never hardcoded).
- `APP_ENVIRONMENT` exports `{ env: 'dev' | 'prod', label }` for UI
  badges / DEV indicators.
- `googleSignIn.ts` logs a helpful hint if the web client ID is missing
  (reminds you to run `npm run oauth:dev`).

## Search Order for the Secret File

The loader looks for `client_secret_*.json` in this order:

1. `--file=<path>` (explicit)
2. `secrets/<env>/client_secret_*.json`
3. `secrets/client_secret_*.json`
4. repo root `client_secret_*.json`

If multiple candidates exist, the env-scoped one (`secrets/<env>/`) wins;
otherwise a warning is printed.

## Usage

```
node scripts/oauth-secrets.cjs dev                  # load dev secrets
node scripts/oauth-secrets.cjs prod                 # load prod secrets
node scripts/oauth-secrets.cjs dev --file=/abs/path/client_secret_x.json
node scripts/oauth-secrets.cjs dev --print          # print client_id only
node scripts/oauth-secrets.cjs dev --if-missing-ok  # exit 0 + warn if absent
node scripts/oauth-secrets.cjs dev --quiet          # suppress output
```

## CI

The release pipeline does **not** depend on local secret files:

- Android: passes `-PGOOGLE_WEB_CLIENT_ID` / `-PAPPLE_SERVICES_ID` from
  GitHub Actions **variables** (`vars.GOOGLE_WEB_CLIENT_ID`) — these take
  priority over the gradle-secrets files.
- iOS: regenerates `.env` per matrix entry from the same `vars.*`.

So CI never needs `client_secret_*.json` checked in.
